**하비데이 접속·채팅·영상 업로드 불안정 분석 — 2026-09-12**

현재 가장 근거가 강한 원인은 이전 앱과 현재 API의 호환성 문제, 요청 지연·실패를 회복하지 못하는 화면 처리, 모바일 환경에 취약한 영상 업로드 방식이다. 이번 관측으로는 서버 자원 부족이 주원인이라고 판단할 근거가 부족하다. 유료 서버로 바꾸기 전에 아래 결함을 먼저 해결하는 것이 타당하다.

- 실제 소스의 콜백을 추출해 실패·미응답을 주입한 제어 실험을 수행했다. 사용자의 실제 휴대폰 증상을 그대로 재현한 실험은 아니다.

**운영에서 확인한 사실**

Supabase 프로젝트는 `ACTIVE_HEALTHY`, 서울 리전이었다. 조회 순간 DB 교착과 활성 잠금 대기를 발견하지 못했다. CPU·메모리·네트워크의 장기간 추이를 확보한 것은 아니므로, 이 스냅샷으로 과거의 모든 장애를 부정할 수는 없다.

24시간 API 게이트웨이 로그 4,733건 중 5xx와 429는 없었다. 4xx는 19건이었다. 별도 Edge Function 로그에는 401 4건, 405 6건이 있었다. `bad_jwt` 4건의 호출자는 Deno Edge Runtime이므로 이를 사용자의 로그인 실패로 합산하지 않았다.

| API | 관측 요청 수 | 서버 측 origin_time 중앙값 | 95백분위 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| 모임 목록 `session_list` | 199 | 35 ms | 510 ms | 847 ms |
| 1:1 채팅 목록 `my_chats` | 68 | 16.5 ms | 65.2 ms | 75 ms |
| 모임 채팅 목록 `my_session_chats` | 68 | 18 ms | 60.6 ms | 75 ms |

| 인증 경로 전체 | 181 | 75 ms | 647 ms | 2,664 ms |

이 값은 Supabase 로그의 `response.origin_time` 집계다. 휴대폰에서 버튼을 누른 뒤 화면이 완성될 때까지의 시간이 아니다. 단말 통신, 렌더링, 인증 선행 대기, 서버에 도달하지 못한 요청은 별도로 측정해야 한다. 인증 경로 전체에는 로그인·설정 등 여러 종류의 요청이 포함된다.

누적 DB 쿼리 평균 실행 시간도 모임 목록 6.05 ms, 1:1 채팅 목록 4.66 ms, 모임 채팅 목록 6.02 ms, 배지 조회 12.97 ms였다. 평균 수백 ms의 상위 쿼리는 확장·타임존·함수 목록 등의 메타데이터 조회였다. 전체 누적 시간이 크다는 이유만으로 앱의 주 병목으로 취급하지 않았다.

**1. 이전 앱이 없어진 API를 호출한다 — 운영에서 확인**

아이폰 웹뷰 형태의 User-Agent에서 다음 요청이 발생했다.

| 호출 | 오류 | 횟수 | 현재 운영 DB |
| --- | --- | ---: | --- |
| `my_credits` | 404 | 2 | 함수 없음 |
| `my_videos` | 404 | 2 | 함수 없음 |
| `my_confirm_proposals` | 404 | 1 | 함수 없음 |

현재 소스와 동기화된 네이티브 자산에서는 이 호출을 찾을 수 없다. 따라서 이전 코드가 담긴 설치 앱 또는 오래된 클라이언트가 현재 서버에 연결되고 있다는 강한 단서다. User-Agent만으로 정확한 앱 버전이나 사용자까지 확정할 수는 없다. 현재 영상 조회 함수 `my_video_posts`와 두 채팅 목록 함수는 운영 DB에 존재한다.

`web/capacitor.config.ts`는 `webDir: "out"`으로 앱 안에 화면 코드를 묶고 `server.url`은 사용하지 않는다. **웹 배포를 완료해도 기존 설치 앱의 화면 코드는 교체되지 않는다.** 반면 운영 DB 변경은 기존 설치 앱에도 즉시 영향을 준다. 앱 업데이트가 모든 사용자에게 도달하기 전에 이전 API를 삭제하면, 앱과 DB가 서로 다른 계약을 사용하는 기간이 생긴다.

권장 대응은 배포된 앱 빌드와 API 계약을 대조하고, 이전 앱이 필요로 하는 읽기 API의 안전한 호환 계층 또는 업데이트 경로를 마련하는 것이다. 폐지한 크레딧 보상을 다시 활성화해서는 안 된다. 새 업데이트 안내 코드가 없는 구버전에는 새 안내 자체도 도달하지 않으므로 안내 UI만으로 해결됐다고 판단하면 안 된다.

**2. 홈 → 채팅 이동 시 한쪽 요청이 다른 쪽 화면까지 막는다 — 코드·제어 실험 확인**

`web/src/app/chat/page.tsx:111`은 1:1 목록과 모임 목록을 `Promise.all`로 함께 기다린다. `:210`의 로딩 조건도 두 목록 중 하나만 `null`이어도 참이다.

- 1:1 목록은 성공했어도 모임 목록이 미응답이면 성공한 목록을 표시하지 않는다.
- 한쪽이 오류를 `null`로 반환하면 전체 화면에는 계속 ‘불러오는 중’이 표시된다.
- 사용자가 실패와 빈 목록을 구분할 수 없고, 목록별 재시도 버튼이 없다.
- 채팅 목록 함수에는 취소 신호가 전달되지 않는다. 상위 코드의 `signal.aborted` 검사는 응답 뒤 상태 변경만 막는다.

`web/src/lib/polling.ts`는 요청 완료 후 다음 조회를 예약한다. 요청 중복을 방지한다는 장점은 있지만, 요청이 끝나지 않으면 다음 조회도 시작하지 않는다. 취소를 따르지 않는 요청을 넣었을 때 화면을 숨겼다 다시 표시해도 새 조회가 시작되지 않는 것을 확인했다. 영원히 끝나지 않는다고 단정하는 대신, 앱 자체가 대기 상한을 정하지 않았다는 점이 문제다.

해결 방향: 탭별 독립 로딩·실패·재시도, 제한 시간과 실제 요청 취소, 이전 성공 목록 유지, 앱 복귀 때의 재연결. 두 요청을 무조건 직렬로 바꾸는 것은 해결책이 아니다.

**3. 채팅 전송 실패가 입력 손실로 이어진다 — 두 채팅에서 재현**

`ChatFrame.submit` (`web/src/app/chat/page.tsx:417`)은 `onSend`가 끝나면 성공 여부와 관계없이 입력을 지운다. 두 전송 함수는 실패 시 경고만 띄우고 정상 반환한다. 실제 콜백으로 확인한 결과, 1:1·모임 채팅 모두 전송 실패 후 입력이 비워졌다. 전송 함수가 예외를 던지는 경우에는 `busy`를 해제할 `finally`가 없어 전송 버튼이 계속 잠길 수 있다.

이는 서버가 느리지 않아도 사용자가 ‘메시지가 사라졌다’, ‘앱이 멈췄다’고 느끼는 직접적인 결함이다. 성공한 경우에만 입력을 지우고, 실패 메시지를 보존하여 재전송할 수 있어야 한다. 중복 전송을 막는 요청 식별자까지 함께 고려해야 한다.

또한 새 메시지는 기본 5초 간격 조회로 확인한다. 메시지 조회는 마지막 ID 이후의 증분 요청이 아니다. 실시간 대화처럼 보이는 화면이지만 수신까지 조회 주기만큼 기다릴 수 있다. 실시간 구독과 복귀 시 동기화를 결합하고, 메시지를 많이 쌓은 방의 페이지 조회를 별도로 검증할 필요가 있다.

**4. 영상 업로드는 실제 파일 크기에 비해 복구 기능이 부족하다 — 운영 크기·코드 확인**

현재 저장된 영상은 7개다. MOV 6개의 평균은 18.74 MiB, 최대는 34.21 MiB이고 MP4 1개는 17.53 MiB다. 모두 6 MiB를 초과한다. 표본은 작고 업로드에 성공해 남아 있는 파일만 포함하므로 실패율로 해석할 수 없다.

`web/src/lib/feedbackVideo.ts:98`은 영상 전체를 표준 업로드로 전송한 다음 썸네일을 올린다. 이어 올리기, 전송률, 사용자 취소, 업로드 단계별 시간 측정이 없다. 썸네일 업로드 실패 시 방금 올린 영상까지 삭제한다. 사용자는 긴 영상 전송부터 다시 시작할 수 있다.

파일을 선택한 직후에는 휴대폰에서 영상 디코딩과 썸네일 생성을 먼저 한다. 여기에는 20초 제한이 있고, 실패하면 새 영상 선택이 완료되지 않는다. MOV 확장자만으로 코덱을 알 수 없으므로 HEVC 문제라고 확정하지는 않았다. 서버에 보내기 전 이 단계에서 느려질 가능성도 분리해서 측정해야 한다.

영상 작성 화면 진입 시 프로필·클라이밍화 검사를 하고, 등록 버튼에서도 다시 검사한다. 그 뒤 파일 전송·썸네일 전송·게시글 생성이 이어진다. 사용자에게는 ‘올리는 중’ 하나로 보여 어느 단계가 멈췄는지 알 수 없다. `beforeunload` 보호만으로 앱 내부 탭 이동이나 OS의 앱 중단을 모두 방지할 수도 없다.

Supabase는 6MB 초과 파일의 안정성을 위해 TUS 이어 올리기를 권장한다. [표준 업로드 공식 문서](https://supabase.com/docs/guides/storage/uploads/standard-uploads)

권장 대응: TUS 전송·진행률·재시도, 영상과 썸네일의 독립 복구, 게시 생성의 기존 중복 방지 유지, 작성 내용 보존. 앱이 종료된 뒤에도 업로드를 계속하려면 웹뷰 TUS만으로 충분하다고 약속하지 말고 네이티브 전송 방식까지 별도로 설계해야 한다. 큰 영상의 압축·코덱 정규화는 실제 기기 성능을 측정하면서 도입한다.

**5. 첫 접속과 복귀 때 로그인 상태 처리가 화면과 강하게 묶여 있다 — 일부 운영 증거, 원인 추가 확인 필요**

실제 로그에서 `refresh_token_not_found`가 5건이었다. 웹과 아이폰 웹뷰에서 모두 발생했다. 이는 로그인 갱신 실패의 증거지만 로그아웃·계정 삭제·기존 세션 만료·테스트 등 구체적 원인은 이 집계만으로 구분되지 않는다.

홈, 채팅, 하단 메뉴가 각각 `currentUser()`를 기다린다. `web/src/lib/supabase.ts:43`의 ‘getSession은 왕복 없음’ 주석은 모든 상황에 맞지 않는다. 설치된 SDK 소스상 만료에 가까운 세션에서는 갱신 요청을 기다릴 수 있다. 현재 SDK 기본 경로는 lockless이므로 흔히 거론되는 Web Locks 교착을 이번 원인으로 단정하지 않았다.

여러 화면이 공유하는 인증 상태와 갱신 결과, 만료·통신 실패 구분, 복귀 시 재확인 절차를 정리해야 한다. 단순 통신 오류에서 무조건 로그아웃시키는 것은 피해야 한다. 세션이 실제로 유효하지 않을 때는 로딩 대신 재로그인을 안내해야 한다.

**6. 불필요한 재조회와 외부 초기 리소스 의존 — 개선 후보**

- 홈은 처음부터 모임뿐 아니라 사람·공개 성취 정보·장소·신청·알림을 조회한다. 모임 표시와는 분리돼 있지만 느린 네트워크의 동시 요청량을 늘린다.
- 홈과 하단 메뉴가 같은 `inbox_counts`를 각각 30초 주기로 조회한다. 채팅 화면에서는 목록 15초, 하단 배지 10초, 열린 대화 5초의 조회가 공존한다. 24시간 가장 많이 호출된 API도 `inbox_counts`였다. 이것만으로 서버 과부하가 확인된 것은 아니다.
- 홈·채팅 목록은 화면별 로컬 상태라 다시 마운트되면 초기 로딩부터 시작한다. 사용자별 짧은 캐시와 뒤에서 갱신하는 방식을 검토하되 로그아웃·차단·삭제 때 무효화해야 한다.
- `web/src/app/layout.tsx`는 외부 jsDelivr 글꼴 CSS를 일반 stylesheet로 불러온다. 네이티브 앱에서도 외부 CSS를 기다리는 경로가 남는다. 첫 접속의 추가 지연 후보이며 이번에 CDN 장애를 관측한 것은 아니다. 앱에 글꼴을 포함하거나 초기 렌더링을 막지 않도록 정리한다.
- 스플래시는 자체 애니메이션으로 약 600ms 뒤 사라지므로, 수초~수십 초 지연을 스플래시 의도적 대기 하나로 설명할 수 없다.

| 5 | 실시간 채팅과 기기별 성능 계측, 외부 글꼴 의존 정리 | 수신 지연·초기 표시 시간·업로드 실패 위치를 지속 측정 |

계측은 첫 단계부터 함께 넣는 것이 좋다. 앱 버전/빌드, OS, 화면, 요청 종류, 소요 시간, 오류 종류를 기록하고 메시지 본문·토큰·개인 사진 경로는 기록하지 않는다. 현재 소스에는 이 사용자 경로를 연속으로 추적하는 원격 성능·오류 수집이 없어, 장애 순간을 사후 대조하기 어렵다.

수정 후에는 실제 아이폰·안드로이드에서 첫 실행, 30분 이상 백그라운드 후 복귀, 만료된 세션, 느린 LTE, Wi-Fi 전환, 채팅 목록 한쪽 실패, 전송 중 실패, 20~35MB MOV 업로드를 검증한다. 빌드·타입·정상 경로 테스트 통과만으로 이 문제가 해결됐다고 판단하지 않는다.

유료 서버 증설은 이후 CPU·연결 포화·DB 대기·서버 응답 지연이 관측될 때 판단한다. 현재 확인된 API 부재, 로딩 결합, 전송 실패 시 입력 삭제, 이어 올리기 부재는 요금제만으로 해결되지 않는다. 현재 네이티브 화면 수정은 새 앱 빌드 배포가 필요하고, 서버 API 호환성 조정은 별도 DB 검토 후 기존 앱에도 적용할 수 있다.

제어 실험은 `node docs/audits/2026-09-12/reproduce-instability.cjs`로 실행한다. 현재 결함의 존재를 확인하는 분석용 스크립트이며, 수정 후 계속 통과해야 하는 회귀 테스트가 아니다. 실제 소스가 바뀌면 수정된 동작을 기준으로 별도 회귀 테스트를 작성해야 한다.
