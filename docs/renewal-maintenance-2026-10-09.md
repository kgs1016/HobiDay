# 리뉴얼 기간 접근 제한

사용자 요청: `line19981016@gmail.com` 계정은 개발을 계속하고, 나머지 사용자에게
‘리뉴얼 준비 중’ 안내를 표시한다. 기존 데이터와 사용자 계정은 유지한다.

## 동작

- 운영 DB의 `app_testers`에 지정 계정 하나를 등록한다. 이메일이 아니라 인증된 user ID로 판정한다.
- `app_maintenance.enabled`가 true이면 웹의 일반 화면과 하단 메뉴를 숨긴다.
- 로그인, 비밀번호 재설정, 인증 콜백, 고객센터, 약관, 개인정보처리방침,
  `/account/delete`는 계속 접근할 수 있다. 계정 변경 시 이전 허용 상태를 즉시 지운다.
- `app_access_status()` 조회 실패 시 일반 화면을 열지 않고 재확인 버튼을 제공한다.
- 기존 SECURITY DEFINER RPC는 Data API의 `check_app_maintenance` 사전 검사로 차단한다.
  직접 테이블 접근과 Realtime에는 추가 제한 RLS를, Storage에는 별도 제한 RLS를 적용한다.
- 자기 미디어 읽기·삭제는 기존 권한 범위에서 유지하여 탈퇴를 지원한다.
- 모임·리뷰 안내와 자동 정리 작업의 활성 상태를 저장한 뒤 잠시 중지한다.
  푸시 대기열은 테스트 계정 수신분만 가져가며, 일반 사용자에게 즉시 발송하는 경로도 제한한다.
- 예전 출시 대기 화면을 가진 앱에는 `app_flags()`도 닫힌 값과 안내 제목을 반환한다.

## 설치 앱의 한계

현재 iOS/Android 1.1.2는 폰 안의 정적 파일로 화면을 표시한다. 9월 정식 오픈 때
대기 화면을 제거했으므로 웹 배포로 기존 앱의 화면을 교체할 수 없다.
서버 접근 제한은 즉시 적용되지만, 새로운 ‘리뉴얼 준비 중’ 안내 화면은
이 변경이 포함된 네이티브 빌드 설치 후 표시된다. 새 빌드는 TestFlight/내부 테스트로도 배포할 수 있다.
계정·패키지 이름·서명키는 유지한다. 이 작업은 스토어의 게시 취소나 앱 삭제를 실행하지 않는다.

## 운영 순서

1. 새 `20261009120000_renewal_maintenance.sql`만 적용한다. 처음에는 enabled=false이다.
   적용 이력도 같은 버전으로 기록한다. 과거 SQL은 재실행하지 않는다.
2. 웹 배포가 성공하고 로그인·접근 제한 화면을 검증한다.
3. `supabase/ops/renewal-close.sql`을 실행해 지정 계정 등록과 접근 제한을 함께 활성화한다.
   예상치 않은 다른 테스트 계정이 있으면 전체 트랜잭션이 중단된다.
4. 비로그인·일반 회원의 Data API 거절, 테스트 계정의 접근 허용, 정리 작업 중지를 확인한다.

재오픈 요청 시 `supabase/ops/renewal-reopen.sql`을 실행한다. DB 플래그를 해제하고
중지 전 활성 상태로 자동 작업을 복구한다. 웹 안내는 재접속 또는 30초 이내 확인 후 사라진다.
완전히 기능을 철회해야 하면 배포 전 저장한 함수 정의·권한·설정과 Git 변경을 사용한다.
